KEY 2 · 需求澄清

AI 动手设计之前，需求理解这个环节如何明确化、可控化、可追溯？

AI 无法像人类设计师那样靠上下文经验和随时追问 PM 来弥补需求缺口。我们区分出两类性质完全不同的信息缺口，并为每类缺口设计了不同的解法。

上下文缺口

客观存在，但 AI 不知道

→ 用知识库注入解决
规格缺口

文档没写清，需要人来补

需求文档没写清楚的东西，只有提需求的人知道。

→ 用澄清对话解决

关键判断：不要把上下文缺口丢给澄清对话。如果 Agent 反复问设计师「这个页面长什么样」——这是知识库没建好，而不是澄清姿势错了。

KEY 2 · 需求澄清

完整交互流程

严格按顺序执行，不允许跳过 Step 2 直接提问，不允许无脑套通用模板

Step 0

用户提交遵守规范

只上传 PRD，不做多余操作。可选附带相关页面截图（不强制）。大部分信息 Agent 自己从文档提取。

Step 1

Agent 读取理解自动解析

自动提取：涉及模块 / 需求类型 / 涉及角色 / 涉及端 / 是否跨页。结合知识库形成初步理解。推断不出的 → 进入澄清环节。

Step 2

需求理解摘要共同确认

输出结构化摘要：目标 / 模块页面 / 核心交互流程 / 角色。明确标注「我目前不确定的地方」。用户先纠错，再回答问题。

Step 3

澄清问题清单优先级分级

关键问题：影响核心设计方案，必答。重要问题：影响交互细节，建议答。次要问题：给默认假设，错了再纠正。其它补充：说明需要什么、为什么需要。

Step 4

吸收回答 · 判断追问≤ 2 轮

把新信息纳入需求理解。仍有关键缺失 → 进入第二轮追问。信息已足够 → 直接输出确认书。

Step 5

需求理解确认书结构化交付

问 vs 不问 · 判断准则

澄清问题越精准，用户体验越好 —— 宁可错一个小细节，也不要让用户答 20 个问题

要问
  • 直接影响页面布局 / 交互结构的信息
  • 文档有歧义或矛盾的地方
  • 有多个合理方案需要用户选择
不要问
  • 能从知识库推断的内容（知识库该补的不要给用户）
  • 纯视觉细节（颜色 / 字号 / 间距由规范决定）
  • 技术实现细节

黄金法则：如果一个问题的答案不会改变设计方案的核心结构，就不要问。

KEY 3 · 输出协议

输出协议设计

AI 输出什么？用什么格式？怎么解析？这三个问题必须事先想清楚

8 字段结构化 JSON 输出合约
// AI 必须按这个吐
{
  thinking,          // 推理过程（思维链）
  summary,           // 本次生成摘要
  selected_components, // 选用组件清单
  render_mode,     // "json" | "code"
  code,             // JSX（code 模式）
  spec,             // json 渲染描述对象
  annotations,    // Inspect 标注数据
  pages            // 多页面路由信息
}
3 层兜底解析器

第 1 层　严格 JSON.parse() —— 最快路径，绝大多数情况

第 2 层　字段逐一正则提取 —— 应对 AI 输出格式轻微偏差

第 3 层　代码块兜底 —— 从 Markdown 代码块中提取可用内容

AI 的输出永远不是 100% 规则的 —— 解析器的鲁棒性决定了系统的稳定性。

KEY 3 · 输出协议

AI 的输出不是给人看的文本，而是要被机器精确解析、实时渲染为真实 UI

这意味着输出格式必须严格可控——既要约束 AI「按什么结构写」，又要在 AI 输出偏差时有兜底解析能力。输出协议的设计质量直接决定了平台的可靠性和用户体验。

✗ 自由文本 / Markdown
  • 无法直接渲染为可交互 UI
  • 格式不稳定，下游解析成本极高
  • 无法携带结构化元信息（标注、路由）
✓ 结构化 JSON 合约
  • 字段固定，前端可直接 parse 并渲染
  • thinking / spec / annotations 关注点分离
  • 支持多渲染模式在同一协议内切换
KEY 3 · 输出协议

8 字段输出合约

AI 的每一次输出都必须严格遵循这 8 个顶层字段——前端按字段分流处理

thinking

推理过程

Chain-of-Thought 思维链——强制 AI 先分析场景再动手，提升输出质量

summary

生成摘要

本次生成的简要说明，前端直接展示为对话气泡，设计师一目了然

selected_components

选用组件

AI 本次选用的大麦 B 端组件清单，供组件映射校验与追踪

render_mode

渲染模式

"json" 或 "code" —— 决定下游走 JSON Spec 渲染引擎还是 React 代码沙箱

code

JSX 代码

code 模式时携带完整 React 组件代码，所有组件已全局注入无需 import

spec

JSON 描述对象

json 模式时携带扁平化 UI 描述（root + elements map），可被 JSON 渲染引擎解析为真实 UI

annotations

交互标注

关键交互节点的结构化描述，供 Inspect 模式高亮叠加展示

pages

多页面路由

多页面场景下的路由信息数组，每项含 title + code/spec

KEY 4 · 渲染引擎

一套渲染引擎不够用——不同场景需要不同的渲染策略与预览方式

B 端设计场景的复杂度由浅到深：从高度标准化的列表 / 表单页，到自由探索性的复杂交互页。单一渲染方案要么牺牲灵活性，要么牺牲规范一致性。因此：双引擎并行 + AI 自主选择 + 适当降级。

双渲染引擎对比

JSON SCHEMA 模式

结构化 · 精确 · 零漂移

基于 @json-render/react + @ali/maiui，通过 JSON Spec 描述页面结构。

  • Zod Schema 校验，类型安全
  • 35+ 大麦 B 端标准组件直接映射
  • 列表页 / 表单页 / 详情页 — 标准 B 端页面
  • 像素级还原设计规范，零视觉漂移
  • 组件间状态由 StateProvider 统一驱动

适合：需求明确的标准 B 端页面

JSX CODE 模式

灵活 · 自由 · 探索性

基于 react-runner，在浏览器端实时编译执行 LLM 生成的 JSX。

  • react-runner + Babel 浏览器端即时编译
  • 自由组合任意组件 + 自定义逻辑
  • 复杂交互 / 特殊布局 / 探索性需求
  • 支持多页面导航（platformNavigate 注入）
  • import 自动剥离 → scope 注入（零 CDN 依赖）

适合：复杂交互 / 非标页面 / 快速探索

AI 自行判断用哪种模式——通过 render_mode 字段决策，无需用户手动切换。

KEY 5 · 迭代编辑

多轮迭代编辑

让 AI 记得上次生成了什么——不是每次都从零开始

没有上下文注入时

「把按钮颜色改成蓝色」

AI 重新生成了一个完全不同的页面。原因：AI 不知道「当前画布」是什么。

注入当前画布上下文后

每次请求时，自动将当前画布代码注入到用户消息中。AI 看到完整上下文，精准修改对应部分，保留其余所有内容不变。

上下文注入逻辑（简化）
function buildIterativeMessage(userRequest, currentCanvasCode) {
  return `
    当前画布代码（请在此基础上修改）:
    ${currentCanvasCode}

    用户请求: ${userRequest}
  `;
}

上下文感知，是让 AI 从「生成工具」升级为「协作伙伴」的关键一步。

KEY 5 · 迭代编辑

让 AI 从「一次性生成」升级为能记住上下文、能持续协作的设计伙伴

单轮生成只能完成 Demo；真正可用的设计需要多轮打磨。这要求平台在「上下文注入」「对话管理」「历史检索」三个维度同时做好，才能让 AI 像人类设计师一样持续迭代。

无上下文

每次从零开始

用户说「把按钮改成蓝色」，AI 重新生成了一个完全不同的页面——因为它根本不知道当前画布长什么样。

对话历史丢失

无法持续协作

刷新页面或切换任务后，之前的设计对话全部消失，用户需要从头描述需求。

多页面缺乏组织

检索和隔离做不到

一个产品有数十个页面，每个页面有多轮设计迭代，缺乏有效的组织和检索手段。

可复用的经验

从这个项目提炼出来 —— 适用于任何 AI Coding 构建 AI Agent 系统的场景

01

架构先于代码

先想清楚核心问题是什么、边界在哪里，再让 AI 动手。没有架构思考的 AI Coding，是「更快速地走错路」。把系统拆成相互独立的层，每层有清晰的输入输出边界。

02

领域知识 = 你的竞争壁垒

AI 是通才，你才是领域专家。你对业务和设计规范理解越深，喂给 AI 的知识质量越高，输出就越强。把知识显式地文档化，是让 AI Coding 长期稳定的唯一方式。

03

协议设计决定系统稳定性

定义清晰的输出协议（格式、字段、容错），并为不合规输出设计多层兜底解析器。AI 的输出永远不是 100% 可预测的 —— 系统的鲁棒性决定了它能不能在生产环境跑起来。

04

小步验证，不积累未验证假设

每写完一个模块，立刻用真实数据验证。不要等全部写完再测，假设越早暴露越早修复，成本最低。感觉对 ≠ 验证过，这个区别会在最错误的时机暴露。

05

规则文件化，而非窗口口头约定

CLAUDE.md + rules 文件是 AI 的「长期记忆」—— 把项目约束、编码规范、禁止行为写进文件，而不是每次在 prompt 里重复说。这是让 AI 跨会话保持一致行为的基础。

06

你是决策者，AI 是执行者

关于产品形态、用户体验、优先级的决策，必须人来做。AI 的方案可以参考，但不能盲目采纳。产品设计师的业务判断力 + AI 的执行效率，才是这套模式真正的威力。

与 AI 协作的 5 条黄金法则

这些规则适用于所有 AI Coding 工具，无论是 Claude Code、Cursor、Copilot 还是扣子编程。

01 先想后做Think Before Code

需求不确定时，先把假设说清楚，不要默认一个方向。有多种方案时，让 AI 列出选项，你来拍板。

✓ 「先列出 3 种实现方案，我选一个再开写。」
✗ 「帮我实现这个功能。」（它选了一个你不想要的方案）

02 极简主义Keep It Simple

只写解决当前问题所需的最少代码。100 行能做完，不要写 1000 行。没要求的抽象和配置，先不要做。

✓ 「只实现核心流程，错误处理和缓存先不要。」
✗ 「帮我搭一套完整、可扩展的系统。」（过度工程化）

03 外科手术式修改Surgical Changes

只改该改的。不要「顺手优化」周边代码，保持原有风格。发现无关问题，可以指出，但未经允许不要改。

✓ 「只改登录函数的校验逻辑，其他一律不动。」
✗ 「优化这个文件。」（它把整文件重写了）

04 定义「完成」Define Done

动手前先定义验收标准。没有明确终点的任务，AI 要么无限发散，要么过早停住。

✓ 「完成定义：表单提交后出 toast，跳首页，移动端可用。」
✗ 「做完告诉我。」（没有可验证标准）

05 持续验证Verify Incrementally

每完成一步就验证，不要假设成功。AI 会很有把握地说「完成了」——但它可能是错的。

✓ 「每实现一个函数就跑一次测试。」
✗ 「全部做完再测。」（错误堆积，难定位）

3 个致命误区

这些误区不是「新手问题」—— 即使使用了很久 AI Coding 的人也经常犯

01

一次性倾倒所有需求

误区把几千字需求一次性丢给 AI，期望它「一次性做完」

对策拆解为可验证的小步骤，每步 ≤ 1 个明确目标

信息量 ≠ 有效性。5 条精确指令 > 500 字模糊描述

02

不验证就信任输出

误区AI 说「已完成」就信了，不跑、不测、不看

对策每步都验证：运行代码、检查输出、确认行为

AI 的「自信」和「正确」是两回事，它永远不会说「我不确定」

03

忽视上下文污染

误区一个对话里做了太多不同任务，AI 开始「串台」

对策任务切换时开新对话，或明确告知「忘掉之前的，现在做 X」

上下文窗口是 AI 的短期记忆，被无关信息填满就降智
